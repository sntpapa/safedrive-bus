# SafeDrive — 시내버스 기사용 위험운전행동 자기점검 앱

Kotlin 네이티브 안드로이드 단독 프로젝트. 개인 휴대폰 센서(GPS + IMU)만 사용하며
차량 DTG 단말과 연동하지 않는다.

> **참고용 고지** — 이 앱의 측정값과 판정은 한국교통안전공단 eTAS의 공식 판정이 아니라
> 휴대폰 센서로 계산한 추정치다. 자기점검 용도로만 사용한다. 모든 데이터는 기기 내부에만
> 저장되며 외부로 전송되지 않는다.

| 단계 | 범위 | 상태 |
|---|---|---|

| 2 | 급가속·급출발·급감속·급정지 판정 + TTS 경고 + 오탐 억제 | **완료** |
| 3 | 급좌우회전·급U턴 판정 | **완료** |
| 4 | 제한속도 설정 화면 + 과속·장기과속 판정 | **완료** |
| 5 | 이벤트 저장(Room), 운행 요약 리포트, CSV 내보내기 | **완료** |
| 추가 | 정차 리뷰 (최근 1·3·5분 경고 되돌아보기) | **완료** |
| 추가 | 화면 분리 (주행 / 이력 / 설정 / 진단), 앱 실행 시 자동 수집 | **완료** |

전 단계를 한 번에 구현했다. 임계값과 필터 계수는 실차 데이터로 확정해야 하며,
그 데이터를 한 번의 운행으로 모으기 위해 **게이트가 막혀 경고가 나가지 않은 이벤트도
사유와 함께 전부 저장한다.**

## 판정 신호와 기준표 해석

가감속 4종은 **1초 창의 속도 변화량**으로 판정한다. 기준표가 "초당 N km/h"로
정의돼 있고, IMU 순간 피크를 임계값에 직접 대면 과탐이 심하기 때문이다.
IMU 종가속도는 피크 기록과 경계값 보류 판단에만 쓴다.

기준표에서 판단이 갈릴 수 있는 부분은 다음과 같이 해석했다.

| 쟁점 | 채택한 해석 |
|---|---|
| 급가속 구간의 10~11, 20~21 구멍 | (6~10], (10~20], (20~) 로 확장 |
| 속도 구간을 고르는 기준 | 판정 창 **시작 시점** 속도 |
| 급감속의 "속도 6.0km/h 이상" | 판정 **시점(창 끝)** 속도 |
| 회전 유형의 속도 조건 | 창 **진입 시점** 속도 |
| 급U턴과 급좌우회전 중복 | U턴이 성립하면 직전 급좌우회전을 집계에서 제외 |
| 과속의 "발생" 단위 | 상태 진입 1회. 히스테리시스 3km/h · 2초로 해제 |

## 핵심 설계 결정

### 센서를 서비스 안에서만 등록하는 이유
API 28부터 백그라운드 앱은 연속보고형(continuous) 센서 이벤트를 받지 못한다.
포그라운드 서비스가 떠 있어야 앱이 foreground importance를 유지하고 수집이 이어진다.

### foregroundServiceType = location
API 35에서 `dataSync` 등 일부 FGS 타입에 6시간 타임아웃이 도입됐다. `location`은
대상이 아니므로 8시간 연속 운행에 안전하다. `dataSync`를 쓰면 안 된다.

### wake-up 센서 우선
`getDefaultSensor(type, true)`로 wake-up 변종을 먼저 요청한다. non-wakeup 센서는
AP 서스펜드 구간에서 FIFO 내용이 유실될 수 있다. wake-up 변종이 없는 기기를 대비해
`화면 꺼짐 시 수집 강제 유지`(PARTIAL_WAKE_LOCK) 설정을 두었고 **기본값은 꺼짐**이다.
끊김 기록에 손실이 확인될 때만 켠다.

### 타임스탬프 정합
가속도/자이로/회전벡터는 서로 다른 배치로 도착한다. "가장 최근 값 붙이기"를 쓰면
배칭 1초 환경에서 최대 1초 어긋난 값이 짝지어진다. 가속도계를 마스터 클록으로 두고
보조 센서를 이벤트 타임스탬프 기준으로 선형보간해 `SensorFrame`을 만든다.

### 실측 샘플링률
`registerListener`의 samplingPeriodUs는 힌트일 뿐이다. 이벤트 타임스탬프로 실제 Hz를
계산하고 20Hz 미만이면 센서 연속성 게이트를 막는다. 도착 시각으로 계산하면 배칭 때문에
값이 무의미해진다.

### 경사로 보정
`TYPE_GAME_ROTATION_VECTOR`(자기장 미사용)에서 얻은 회전행렬의 3번째 행으로 매 시점의
중력 벡터를 단말 좌표계에서 산출하고 가속도에서 뺀다. 중력을 폰 좌표계에 고정된 값으로
가정하지 않으므로 경사로에서 중력 성분이 감속으로 오인되지 않는다.
회전벡터를 못 쓰는 기기에서는 `pitchCompensationReliable = false`로 표시된다.

### 거치 이탈 감지
절대 각도만 쓰면 도로 경사(도심 최대 약 7°)와 제동 시 노즈다이브(1~3°)를 이탈로
오인한다. **중력 방향 변화율(°/s)** 을 1차 지표(도로 경사 변화는 통상 5°/s 미만,
폰 탈거는 수십 °/s), 절대 편차 30°를 2차 지표, 비정상 각속도 200°/s를 3차 지표로 쓴다.

## 1단계 완료 기준 확인 방법

디버그 화면에 필요한 값이 모두 노출되어 있다.

| 기준 | 확인 위치 |
|---|---|
| 종방향 가속도가 GPS 속도 변화율과 ±1.5 km/h/s 이내 | `종가속도 - GPS 차이` 항목. 1.5 이하면 초록 |
| 정지 시 종/횡 가속도가 0 근처로 수렴 | `차량 좌표계 운동량` 카드 |
| 화면 끄고 30분 후에도 20Hz 이상 유지 | `실측 샘플링률` + `감지 중단 기록` |
| 거치대에서 뽑으면 즉시 미보정 전환 | `거치 안정성` 게이트 및 `재보정 횟수` |

권장 실차 절차
1. 폰을 거치대에 임의 각도로 고정하고 앱 시작.
2. 정류소 정차 3초 이상 → 중력 축 확정(진행률 40%).
3. 정차→출발→감속 사이클 4~6회 → 전방 축 확정. 통상 2~5분.
4. 정렬 완료 후 주행하며 `종가속도 - GPS 차이`를 관찰.
5. 화면 끄고 30분 주행 후 다시 열어 샘플링률과 감지 중단 시간 확인.
6. 폰을 거치대에서 뽑아 게이트가 즉시 막히는지 확인.

전부 `core/Constants.kt` 한 곳에 있다. 코드 안 다른 곳에 상수를 흩지 않는다.

| 상수 | 현재값 | 재조정 근거가 필요한 이유 |
|---|---|---|
| `SENSOR_BATCH_LATENCY_US` | 1,000,000 | 배터리와 경고 지연의 트레이드오프. 2단계 진입 전 실측 필요 |
| `GPS_ACCURACY_MAX_M` | 20 | 실제 노선의 accuracy 분포를 수집해 결정 |
| `ACCEL_LPF_CUTOFF_HZ` | 2.0 | 실차 FFT로 노면 충격 대역 확인 필요 |

| `MOUNT_DEVIATION_MAX_DEG` | 30 | 위와 동일 |
| `FWD_MIN_SAMPLES` / `FWD_MIN_SEGMENTS` | 300 / 4 | 실제 수렴 시간과 정확도의 트레이드오프 |

## 실차 1차 시험에서 확인된 것 (2026-09-07, 버스 탑승 전 정지 상태)

| 관측 | 원인 | 조치 |
|---|---|---|
| 정지 상태인데 GPS 속도가 3.8~11.2 km/h로 표시 | 도플러 GNSS 속도의 정지 잡음. 이 때문에 "정차" 조건이 성립하지 않아 **좌표계 보정이 0%에서 진행되지 않음** | `suppressStationaryNoise()` 추가. 보고 속도 < 속도정확도(1시그마)면 0으로 간주 |
| 속도가 GPS 게이트 차단 중에도 또렷하게 표시됨 | 신뢰도와 표시가 분리되지 않음 | `speedTrusted` 추가. 미달 시 숫자를 흐리게, "GPS 품질 미달 · 신뢰 불가" 표기 |
| 화면 상단(제목·정지 버튼)이 상태바에 가려짐 | targetSdk 35의 edge-to-edge 강제 적용 | `enableEdgeToEdge()` + `windowInsetsPadding(WindowInsets.safeDrawing)` |
| 실측 가속도계 114Hz (요청 50Hz) | HAL이 요청보다 빠른 native rate로 전달. samplingPeriodUs는 상한 힌트일 뿐 | 기능상 문제 없음. 다만 예상보다 배터리를 더 쓰므로 배터리 실측 시 감안 |
| 손에 들고 있을 때 재보정 7회, "비정상 각속도 209°/s" | 거치 안정성 게이트가 설계대로 동작 | 조치 불필요 |

## 화면 구성 원칙

기사에게 보이는 `주행` 탭에는 **기사가 이해하고 쓸 수 있는 것만** 둔다.
좌표계 보정 진행률, 센서 샘플링률, 게이트 상세 같은 개발자용 수치는 `진단` 탭으로 보냈다.

다만 `감지 중 / 보정 중 / 경고 보류` 상태 한 줄은 주행 화면에 남긴다.
이게 없으면 조용한 이유가 운전을 잘해서인지 앱이 못 잡고 있어서인지 구분할 수 없고,
그러면 기사가 이 앱을 믿을 근거가 사라진다.

주행 화면에는 시작/정지 버튼을 두지 않는다. 운전 중 오터치로 수집이 끊기면
그 구간이 통째로 사라지기 때문이다. 정지는 상단바 알림과 설정 탭에서만 할 수 있다.

## 알려진 제약과 위험

1. **배칭 1초와 실시간 경고의 충돌.** 2단계에서 경고를 붙이면 배치 지연 + TTS 합성 지연이
   더해져 급감속 경고가 2초 가까이 늦을 수 있다. `SENSOR_BATCH_LATENCY_US`를 낮추면
   해결되지만 배터리를 잃는다. 실측 없이 결정할 수 없다.
2. **거치대 미세 회전.** 정렬 완료 후에도 흡착식 거치대가 주행 진동으로 수 도씩 돌아가면
   종/횡 축이 섞인다. 1단계는 초기 정렬까지만 구현했고 완료 후 재추정은 없다.
3. **GPS 속도 지연.** 도플러 기반 속도는 정확하지만 0.5~1초 지연이 있다. 디버그 화면에서
   GPS 속도와 융합 속도를 따로 표시해 실차에서 차이를 확인할 수 있게 했다.
4. **제조사 배터리 최적화.** 8시간 중 서비스가 종료되는 가장 큰 원인. 온보딩에서 안내하고
   `감지 중단 기록`으로 실제 손실을 측정한다.
5. **정밀 위치 권한.** API 31+에서 사용자가 '대략적인 위치'만 허용하면 accuracy가 수백 m가
   되어 GPS 게이트가 상시 차단된다. 온보딩에서 명시적으로 안내한다.
