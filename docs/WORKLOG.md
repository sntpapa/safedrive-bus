# SafeDrive 개발 기록

시내버스 기사용 위험운전행동 자기점검 앱을 만들면서 무엇을 했고, 실차 시험에서
무엇이 틀렸으며, 그것을 어떻게 찾아 고쳤는지의 기록입니다.

작성 기준: 2026-09-12 · 저장소 `github.com/sntpapa/safedrive-bus`

---

## 1. 무엇을 만들었나

개인 휴대폰의 GPS와 관성센서만으로 한국교통안전공단 위험운전행동 8개 유형을 판정하고
음성으로 알려 주는 안드로이드 앱입니다. 차량 DTG 단말을 쓰지 않습니다.

| 항목 | 내용 |
|---|---|
| 스택 | Kotlin 네이티브, Jetpack Compose |
| SDK | compileSdk 35 / minSdk 26 / targetSdk 35, JDK 17 |
| 저장 | Room + SQLite, 기기 내부에만. 외부 전송 경로 없음 |
| 규모 | Kotlin 40여 개 파일, APK 약 15.7MB (도로 데이터 10.6MB 포함) |

### 판정 대상

| 유형 | 속도 조건 | 기준 |
|---|---|---|
| 과속 | - | 제한속도 +20km/h 초과 |
| 장기과속 | - | 위 상태 3분 이상 |
| 급가속 | 6~10 / 11~20 / 21 초과 | 초당 8 / 7 / 6 km/h 이상 |
| 급출발 | - | 5.0km/h 이하에서 초당 8km/h 이상 |
| 급감속 | 30 / 50 이하 / 50 초과 | 초당 9 / 10 / 12 km/h 이상, 속도 6.0 이상 |
| 급정지 | - | 초당 9km/h 이상 감속해 5.0 이하 도달 |
| 급좌우회전 | 25km/h 이상 | 3초 내 누적 60~160° |
| 급U턴 | 20km/h 이상 | 6초 내 누적 160~180° |

급진로변경·급앞지르기·연속운전은 판정하지 않습니다.

## 3. 핵심 설계 결정

### 판정 신호를 GPS 속도로 잡았다

기준표가 "초당 N km/h"로 정의돼 있으므로 **1초 창의 속도 변화량**을 1차 신호로 씁니다.
IMU 종가속도의 순간 피크는 1초 평균보다 훨씬 크게 나와(노면 요철 하나에 10 km/h/s 이상)
임계값에 직접 대면 과탐이 심합니다. IMU는 피크 기록과 경계값 보류 판단에만 씁니다.

이 선택 덕분에 가감속·과속 판정은 좌표계 정렬 없이도 동작합니다.

### 센서를 포그라운드 서비스 안에서만 등록

API 28부터 백그라운드 앱은 연속보고형 센서 이벤트를 받지 못합니다.
서비스 밖에서 등록하면 화면이 꺼지는 순간 데이터가 끊깁니다.

`foregroundServiceType`은 `location`입니다. API 35에서 `dataSync` 등 일부 타입에
6시간 타임아웃이 도입됐는데 `location`은 대상이 아니라 8시간 운행에 안전합니다.

### 타임스탬프 정합

가속도·자이로·회전벡터가 서로 다른 배치로 도착합니다. "가장 최근 값 붙이기"를 쓰면
배칭 1초 환경에서 최대 1초 어긋난 값이 짝지어집니다. 가속도계를 마스터 클록으로 두고
보조 센서를 이벤트 타임스탬프 기준으로 선형보간합니다.

### 4개 게이트, 그러나 유형별로 필요한 것만

| 게이트 | 조건 |
|---|---|
| 좌표계 보정 | 차량 좌표계 정렬 완료 |
| GPS 품질 | 수평정확도 15m 이내 |
| 센서 연속성 | 직전 3초간 끊김 없음, 실측 20Hz 이상 |
| 거치 안정성 | 중력벡터 방향이 급변하지 않음 |

가감속·과속은 GPS 속도만 쓰므로 `GPS 품질 + 센서 연속성`만 봅니다.
요레이트가 필요한 회전만 4개 전부를 요구합니다.

**게이트가 막혀도 판정은 계속하고 이벤트는 기록합니다.** 경고만 나가지 않습니다.
그래야 한 번의 운행에서 "무엇이 몇 번 걸렸고 무엇이 왜 막혔는지"가 모두 남습니다.

## 4. 제한속도 데이터 파이프라인

### 출처

| 데이터 | 역할 |
|---|---|
| ITS 표준노드링크 | 도로 구간별 기본 제한속도. 전국 링크 155만 개 |
| 전국무인교통단속카메라 | 경찰 단속 기준 속도. 노드링크 값을 보정 |
| 전국어린이보호구역 | 제한속도로 쓰지 않음. 판정 보류 플래그로만 사용 |

전국 데이터를 앱에 다 넣을 수 없어 운행 지역(대전+세종)만 잘라 SQLite로 만듭니다.
링크 49,837개, 세그먼트 324,342개, 약 10.6MB. 변환 도구는 `tools/`에 있습니다.

### 어린이보호구역을 제한속도로 쓰지 않은 이유

대전 영역(링크 35,447개, 보호구역 749곳)에서 실측한 결과입니다.

| 보호구역에서의 거리 | 링크 수 | `MAX_SPD`=30 | 40 이상 |
|---|---|---|---|
| 30m 이내 | 315 | 82.5% | 14.9% |
| 100m 이내 | 3,127 | 71.7% | 27.0% |
| 300m 이내 | 15,122 | 50.9% | 47.8% |
| 대전 전체 | 35,447 | 35.3% | — |

**노드링크가 이미 학교 인접 도로의 82.5%를 30km/h로 표시하고 있었습니다.**
반면 어린이보호구역 표준데이터에는 제한속도 컬럼도 구역 경계도 없고 학교 건물 좌표
한 점뿐입니다. 반경 300m로 덮어쓰면 47.8%의 링크가 실제로는 40 이상인데 30이 되어
학교 옆 간선도로가 전부 30이 됩니다.

그래서 제한속도는 노드링크만 쓰고, 보호구역은 "학교 50m 이내인데 제한속도 40 이상"인
링크(대전 194개)에 주의 플래그만 달아 과속 판정을 보류합니다.

### 단속카메라로 보정한 이유

대전 영역 카메라 2,168대를 노드링크와 대조한 결과 **1,296개 링크가 매칭됐고 그중
21.2%가 `MAX_SPD`와 달랐습니다.**

| 불일치 패턴 | 건수 | 결과 |
|---|---|---|
| 링크 50 → 단속 30 | 67 | 과속 **미탐** |
| 링크 30 → 단속 50 | 55 | 과속 **오탐** |
| 링크 60 → 단속 50 | 36 | 과속 미탐 |

양방향으로 틀리므로 카메라 값을 우선 적용합니다.

### 맵매칭

위경도 0.002° 격자 9칸에서 후보 세그먼트를 뽑고, GPS 진행방위와 링크 방위가 50° 넘게
다르면 버립니다(반대 차선·교차 도로 제거). 직전 링크에 4m 가산점을 주어 고가/지하차도를
구분합니다. 2순위가 8m 이내인데 제한속도가 다르면 어느 도로인지 확정할 수 없다고 보고
**과속 판정을 보류합니다.**

주행 중에는 네트워크를 쓰지 않습니다. 터널에서도 조회가 끊기지 않습니다.

## 5. 실차 시험에서 찾아 고친 결함

**이 절이 이 프로젝트에서 가장 중요한 부분입니다.** 전부 실제 운행 데이터로
확인한 것이며, 추측으로 고친 것은 없습니다.

### 5.1 정지 상태인데 속도가 3.8~11.2km/h로 표시

도플러 GNSS 속도는 정차 중에도 자기 속도정확도 수준의 잡음을 냅니다.
표시 문제가 아니라 **좌표계 보정의 "정차" 조건이 성립하지 않아 보정이 0%에서
영원히 멈추는** 문제였습니다.

`Location.getSpeedAccuracyMetersPerSecond()`를 써서 보고 속도가 자기 정확도보다
작으면 0으로 간주하도록 했습니다.

### 5.2 도로 데이터가 통째로 로드되지 않음

`assets.openFd()`는 압축되지 않은 파일에만 동작합니다. `.db`는 APK에서 압축되므로
버전 비교용 크기 조회가 항상 예외를 냈고, 제한속도 매칭이 전혀 되지 않았습니다.
진단 화면에 `도로 데이터: 없음`으로 나타났습니다. 버전 문자열 비교로 바꿨습니다.

### 5.3 전방축 추정이 노면 진동에 오염

2시간 운행 후에도 보정이 82%에서 멈췄습니다. 진단 화면 수치가 원인을 지목했습니다.

| 지표 | 실측 | 기준 |
|---|---|---|
| 전방축 샘플 | 1,081 | 300 |
| 가감속 구간 | 23 | 4 |
| **방향 집중도** | **2.8** | 4.0 |
| **각도 표준편차** | **55.9°** | 12° |

샘플과 구간은 3배 넘게 모였는데 방향이 모이지 않았습니다. 원인은 필터를 거치지 않은
원시 가속도를 쓴 것이었습니다. 노면 진동(±2~3 m/s²)이 실제 종방향 가속(0.8~2 m/s²)보다
컸습니다. 판정용과 같은 2Hz 저역통과를 적용했습니다.

또한 각도 표준편차 기준 12°는 `std = sqrt(-2 ln R)` 이라 평균벡터 크기 0.978을
요구하는 도달 불가능한 값이었습니다. 실측 없이 잡은 값이라 35°로 완화했습니다.

**결과: 방향 집중도 2.8 → 21.3, 각도 표준편차 55.9° → 26.2°, 보정 100% 완료.**

### 5.4 판정이 한 번도 실행되지 않음

판정 호출 전체를 "좌표계 정렬 완료" 조건으로 감쌌습니다. 보정이 0%면 판정이 한 번도
돌지 않아 CSV에 헤더만 남았습니다. 가감속·과속은 GPS 속도만 쓰므로 정렬과 무관하게
판정하도록 분리했습니다.

### 5.5 서비스 재시작 시 운행 기록 초기화

제조사 절전 정책이 서비스를 종료시키면 `START_STICKY`로 되살아나는데, 시작 시각과
누적 거리가 0으로 돌아가 "경고 없이 N분"이 실제보다 짧게 나왔습니다.
5초마다 생존 신호를 남겨 10분 이내 재시작이면 같은 운행으로 이어받습니다.

이어받기 구현 후에도 거리만 0이 되는 문제가 있었는데, 게시 루프의 생존 신호가
이어받기보다 먼저 실행되어 저장값을 0으로 덮어쓰는 경쟁 상태였습니다.

### 5.6 한 번의 제동이 2~3건으로 계상

```
21:24:08  급감속  27.8 km/h  -11.02
21:24:11  급감속   7.1 km/h  -13.54
21:24:12  급정지   0.0 km/h  -14.33
```

정류소 진입 제동 **한 번**입니다. 디바운스가 유형별이라 급감속과 급정지가 따로
세졌습니다. 디바운스를 계열 단위(감속 / 가속 / 회전)로 바꿨습니다.

### 5.7 물리적으로 불가능한 값이 경고로 나감

```
19:24:37  급출발  10.2 km/h
19:24:38  급정지   0.0 km/h   ← 1초 뒤
```

1초 만에 0→10→0은 버스로 불가능합니다. 저속 GNSS 잡음입니다.
가속 계열과 감속 계열이 3초 안에 연달아 나오면 나중 것을 보류합니다.

판정값 자체가 불가능한 경우도 있었습니다. 급출발 15.2와 24.3(1초에 0→24km/h,
6.7 m/s²)인데 대형버스 최대 가속은 1.0~1.5 m/s²입니다.
가속 10, 감속 22 km/h/s를 넘으면 측정 오류로 보고 보류합니다.

### 5.8 이면도로 오매칭으로 과속 오탐

과속 4건이 **전부 제한속도 10km/h 링크**에서 나왔습니다. 주차장 진출입로 같은 링크가
대전 영역에만 1,013개입니다. 16m 옆 이면도로에 매칭되면 30km/h로 달려도 과속이 됩니다.
제한속도 30 미만이면 과속 판정을 보류합니다. 어린이보호구역은 30이라 영향이 없습니다.

### 5.9 GPS가 튀는 구간이 게이트를 통과

```
22:09:25  66.1 km/h   정확도 15.2m   속도정확도 0.88
22:09:34  60.9 km/h   정확도 16.0m   속도정확도 1.07
22:09:38  24.7 km/h   정확도 14.4m   속도정확도 0.73
```

시내버스가 66km/h를 찍을 리 없습니다. 정상 이벤트는 정확도 3~10m에 몰려 있는데
이 구간만 14~16m였고 임계값 20m를 통과했습니다. 15m로 조였습니다.

그리고 **속도정확도를 처음으로 게이트에 넣었습니다.** 1초 차분의 표준편차는
`sqrt(2) × 속도정확도`인데, 1.07 m/s면 5.4 km/h/s로 급가속 임계값 6과 구분되지
않습니다. 판정값이 잡음의 2.5배가 안 되면 경고를 내지 않습니다.

### 5.10 판정값이 기록되지 않음

`최대가감속` 칸에 IMU 피크를 저장해 정렬 전에는 전부 0.00이었고, 급가속 이벤트에
-1.06(감속)이 찍히기도 했습니다. 이벤트가 얼마나 셌는지 알 수 없어 임계값 조정
근거가 없었습니다. 실제 판정에 쓴 값을 `판정값` 컬럼에 저장하고 GPS 속도정확도도
함께 남깁니다.

### 5.11 UI 결함

| 증상 | 원인 |
|---|---|
| 화면 상단이 상태바에 가려짐 | targetSdk 35의 edge-to-edge 강제 적용 |
| 밝은 테마에서 상태 글씨가 안 보임 | 어두운 배경용 색을 밝은 배경에 그대로 사용 |
| 항목명이 한 글자씩 세로로 쪼개짐 | 값에 폭을 주지 않아 항목명 칸이 0까지 눌림 |
| 리뷰 패널이 속도 위에 떠서 버튼 위치가 매번 바뀜 | 배치 순서 |
| 정지를 눌러도 즉시 다시 시작 | 자동 시작이 `serviceRunning=false`를 보고 재시작 |
| 뒤로가기로 앱이 바로 닫힘 | 확인 없음 |
| CSV가 앱 전용 폴더에 저장 | MediaStore 미사용 |

lint가 잡아낸 것도 있습니다. **`VIBRATE` 권한 누락** — 진동은 경고의 주 전달 수단인데
권한 없이 호출하고 있어, 소리가 안 들리는 상황에서 경고가 통째로 사라질 뻔했습니다.
**`resolveActivity()`** 는 API 30+ 패키지 가시성 제한으로 항상 null을 반환해
배터리 설정 버튼이 조용히 죽어 있었습니다.

## 6. 2026-09-08 이후 — 경고가 너무 많다

기사에게서 "경고가 너무 자주 난다"는 말이 계속 나왔다. 실제로 하루 운행에서
**99건 중 67건(68%)** 이 경고로 나갔다. 여기서부터가 그 원인을 파고든 기록이다.

결론부터 적으면 **억제 장치가 전부 좌표계 정렬에 묶여 있었고, 정렬이 끝나지
않았다.** 원인이 하나가 아니라 네 겹으로 쌓여 있었다.

### 5.12 GPS가 급정지를 4배 과대평가한다

정렬이 살아 있던 짧은 구간에서 처음으로 IMU와 GPS를 대조할 수 있었다.

| 유형 | GPS 판정값 | IMU 실측 | 비율 |
|---|---|---|---|
| 급정지 | 2.61 m/s² | **0.61 m/s²** | 24% |
| 급정지 | 3.21 m/s² | **0.49 m/s²** | 15% |
| 급정지 | 2.71 m/s² | **0.83 m/s²** | 31% |
| 급감속 | 2.51 m/s² | 1.55 m/s² | 62% |

0.5~0.8 m/s²는 승객이 아무것도 느끼지 못하는 제동이다. 급정지가 아니다.
급가속·급출발은 **부호까지 반대**인 것이 있었다. GPS는 가속했다는데 IMU는
감속했다고 한다.

도플러 속도는 0.5~1초 늦는다. 제동할 때 GPS 속도가 늦게 떨어지다 한꺼번에
내려가면 그 1초 차분이 실제보다 훨씬 커진다.

`peakLongitudinal`은 판정 창의 **최대값**이므로 진짜 이벤트라면 GPS 1초 평균보다
작을 수 없다. 이 모순을 억제 조건으로 삼았다(`MIN_IMU_AGREEMENT_RATIO = 0.5`).

### 5.13 거치 변화율은 거치 이탈이 아니라 차량 기동을 잡고 있었다

중력 방향 변화율을 거치 이탈의 1차 지표로 썼다. 도로 경사 변화는 5°/s 미만,
폰 탈거는 수십 °/s이므로 구분된다고 보았다. 틀렸다.

| 실측 | 임계 | 재보정 |
|---|---|---|
| 2026-09-08 (1시간 44분) | 25°/s | 10회 (5.7회/시간) |
| 2026-09-09 (3시간 34분) | 45°/s | 20회 (5.6회/시간) |

**임계값을 올려도 시간당 빈도가 그대로였다.** 임계값 문제가 아니다.

이 벡터는 `GAME_ROTATION_VECTOR`가 가속도계를 참조해 만든다. 버스가 좌회전하면
횡가속 3 m/s²가 중력과 합쳐져 겉보기 중력이 17° 기울고, 진입·이탈이 0.5초면
변화율이 수십 °/s가 된다. **거치 이탈이 아니라 차량 기동이다.**

무효화 사유에서 빼고 진단 표시용으로만 남겼다. 절대 편차 30°와 비정상 각속도
200°/s가 진짜 지표다. 폰을 빼면 편차가 즉시 30°를 넘지만 차량 기동으로는
17° 수준이라 넘지 않는다.

**결과: 재보정 20회 → 0회.**

### 5.14 자이로 스파이크 하나로 정렬이 리셋됐다

변화율을 뺐더니 재보정 사유가 `비정상 각속도`로 바뀌었고, 5시간 운행에 **41회**가
나왔다. 7분마다 정렬이 처음부터 다시 시작된 셈이다.

기록된 값이 203~230°/s로 임계 200을 겨우 넘는다. 폰을 실제로 손에 쥐면
수백~1000°/s가 나오고 그 상태가 이어진다. **이 값들은 센서 스파이크다.**
자이로는 FIFO가 없어(`0/10000`) 순간 피크가 배칭 없이 그대로 들어온다.

거치 편차와 변화율에는 지속 조건이 있었는데 **이 검사에만 없었다.**
200ms 지속 조건을 넣었다.

### 5.15 각도 표준편차는 축이 아니라 부호를 본다

재보정이 잡히자 이번엔 마지막 한 조건에서 막혔다.

| 조건 | 관측 | 기준 | |
|---|---|---|---|
| 전방축 샘플 | 3561 | 300 | 12배 통과 |
| 가감속 구간 | 37 | 4 | 9배 통과 |
| 방향 집중도 | 18.5 | 4.0 | 4.6배 통과 |
| **각도 표준편차** | **62.9°** | 35.0° | **실패** |

두 지표가 재는 것이 다르다. 고유값비는 **축**의 명확성(180° 대칭이라 부호에 둔감),
각도 표준편차는 샘플이 앞/뒤 어느 쪽을 향하는지의 **부호** 일치도다.

`R = exp(-std²/2)`, 앞/뒤로 갈릴 때 `R = |2q-1|`이므로 표준편차는 곧 다수결의
여유다. 35°는 **91:9** 를 요구하는데, GPS 지연이 있는 한 도달할 수 없다.

그리고 이 값은 샘플이 쌓이는 동안 크게 요동친다.

| 샘플 | 고유값비 | 표준편차 |
|---|---|---|
| 510 | 12.3 | 90.1° |
| 912 | 18.2 | 81.8° |
| 3561 | 18.5 | 62.9° |

35 → 90 → **110°** 로 두 번 올렸다.

### 5.16 그런데 축이 통째로 뒤집혀 있었다

정렬이 완료되자 더 나쁜 것이 드러났다. GPS와 IMU의 **부호 일치율이 18~58%** 였다.
동전 던지기와 다를 바 없고, 08~09시대는 오히려 반대가 더 많았다.

```
07:05:59  급감속  GPS -10.03   IMU -1.08
07:08:05  급가속  GPS  +7.58   IMU -2.14   <- 가속인데 IMU는 음수
07:14:28  급가속  GPS  +9.46   IMU -2.12   <- 가속인데 IMU는 음수
```

IMU가 가속이든 감속이든 한 방향으로 고정돼 있다. 전방축이 실제 진행방향과 거의
직각으로 잡혀 종방향 성분이 거의 없고 치우친 잡음만 남은 것이다.

**IMU 교차검증이 사실상 무작위로 억제하고 있었다.** 억제가 많이 걸린 것도
"운 좋게" 맞은 것일 수 있다는 뜻이다.

표준편차 같은 간접 지표를 추측하는 대신 **정답과 직접 맞춰 보기로** 했다.
정렬이 끝난 뒤에도 GPS 속도 증감 부호와 IMU 종가속도 부호를 계속 대조한다.

| 일치율 | 조치 |
|---|---|
| 30% 이하 | 축을 **뒤집는다** |
| 70% 이상 | IMU 교차검증을 쓴다 |
| 그 사이 | 축이 비스듬한 것 → 교차검증을 **쓰지 않는다** |

### 5.17 정렬을 기다리는 설계 자체가 잘못이었다

세 번을 고쳤는데도 어떤 기기에서는 정렬이 끝나지 않았다. 억제 장치 전체가
정렬에 묶여 있는 한 그 기기에서는 아무것도 걸러지지 않는다.

**수평 가속도 크기**를 새 신호로 넣었다. 중력 방향만 알면 구해지므로 정렬이
필요 없다. 종방향 가속은 이 크기의 한 성분이라 크기를 넘을 수 없다.

이 검사는 **한쪽으로만 틀린다.** 크기는 종방향의 상한이므로 크기가 작으면
종방향도 확실히 작다. 노면 진동은 크기를 키우는 방향이라 억제를 덜 하게 만든다.
놓치는 일은 있어도 멀쩡한 이벤트를 지우지 않는다.

정렬이 끝나면 종방향 직접 대조로 자동 전환된다. 그쪽이 훨씬 강하다.

### 5.18 결과

| 구간 | 건수 | 경고 | 비율 |
|---|---|---|---|
| 2026-09-09 이전 (v0.10.0) | 99 | 67 | **68%** |
| 정렬 미완료 구간 | 31 | 10 | 32% |
| **정렬 완료 구간** | 31 | **2** | **6%** |

정렬 완료 후 1시간 동안 경고는 2건이었고, 그중 하나는 제한 50 구간에서
70.6km/h — **정당한 과속 경고**였다.

### 5.19 운행이 끝났는데 앱이 계속 기록한다

앱 안의 5분 정차 팝업은 화면이 켜져 있어야 보인다. 화면을 끈 채 하차하면
아무도 못 본다. 그 결과가 데이터에 그대로 남았다.

| 사례 | 내용 |
|---|---|
| 도보 혼입 | 하차 후 걷는 구간에서 `급가속 16.0 km/h` 경고 발생 |
| **자가용 혼입** | 23시대에 `과속 105.9 km/h`, `급가속 113.9 km/h`. 시내버스로 불가능하다 |

두 번째가 심각하다. 146번 기사 데이터에서 **과속 경고 21건 중 18건이 퇴근길
자가용 구간**이었다. 거리와 시간이 부풀려지면 100km 환산이 통째로 틀어진다.

정차 임계를 5분 → 3분으로 낮추고, **별도 알림 채널**로도 묻게 했다. 포그라운드
알림은 `IMPORTANCE_LOW`라 조용하지만 이건 놓치면 안 되므로 `DEFAULT`로 뒀다.

### 급가속은 판정 신호 자체가 틀렸다

공식은 **한 달간 0.00건**이다. 같은 기사, 같은 버스, 같은 노선인데 우리 앱은
하루에 **47건**을 판정했다.

12절에 적어둔 "기준표 6~8 km/h/s가 버스 물리 성능(3.6~5.4)을 초과한다"가
공식 데이터로 확인됐다.

## 9. 음성 경고가 들리지 않는다

"`급감속`의 `급`이 안 들린다"는 구체적인 보고가 있었다.

`requestFocus()` 바로 다음 줄에서 `speak()`를 호출하고 있었다. **오디오 경로가
열리기 전에 발화가 시작된다.** 블루투스 전환은 200~500ms, 스피커 깨우기도
50~150ms가 걸린다.

하필 `급`이 가장 취약한 음절이다. `ㄱ`은 파열음, `ㅡ`는 에너지가 낮은 모음,
`ㅂ` 받침은 소리가 거의 없는 미파음이라 셋 다 짧고 약하다.

| 조치 | 내용 |
|---|---|
| 선행 무음 150ms | 오디오 경로를 먼저 연다 |
| 경고음 2.2kHz · 120ms | 소음은 100~300Hz 저음에 몰려 있어 그 대역을 피한다 |
| 피치 1.0 → 1.15 | 목소리 기본 주파수를 소음 대역에서 밀어 올린다 |

경고음은 `AudioTrack`으로 직접 생성한다. 음성과 같은 `AudioAttributes`를 써야
카오디오·블루투스로 함께 나가기 때문이다. `ToneGenerator`는 스트림 타입만 받아
라우팅이 갈린다.

이후 "경고음이 너무 크다"는 보고를 받아 설정 화면에 **경고음 크기·음성 높낮이·
속도·시험 재생**을 넣고, 음성과 경고음을 각각 끌 수 있게 했다.

## 10. 화면에 무엇을 보여줄 것인가

주행 화면 타일이 **판정에 걸린 전체 건수**를 보여주고 있었다. `급감속 41`로
뜨는데 실제 경고는 1건이었다. 기사는 이것을 "내가 41번 거칠게 밟았다"로 읽는다.

개발자에게 필요한 숫자를 기사 화면에 올려둔 것이 잘못이었다.

| 화면 | 바꾼 것 |
|---|---|
| 주행 타일 | 걸린 횟수 → **경고 건수** |
| 주행 `/100km` | 경고 기준으로 바뀜 (공식 eTAS와 같은 잣대) |
| 주행 하단 안내문 | "N건은 측정을 신뢰할 수 없어…" 삭제 |
| 이력·CSV·진단 | 그대로 (분석용) |

**기록은 반드시 남긴다.** 이 절의 모든 발견이 억제된 건들의 기록에서 나왔다.
경고만 저장했다면 하루 데이터가 3건이었고 아무것도 알 수 없었다.

## 11. 운행 단위를 다시 정의했다

운행 하나 = **앱 실행부터 종료까지**다. 그 사이의 휴게·정차·화면 꺼짐·
백그라운드는 전부 같은 운행으로 이어진다.

끝나는 경우는 셋뿐이다 — 3분 정차 확인에서 `운행 종료`, 앱 종료(뒤로가기),
자정.

### 이어받기에서 시간 창을 없앴다

마지막 생존 신호로부터 10분 안에 되살아난 경우만 이어받았다. 그러면 **30분
휴게 중에 절전 정책이 프로세스를 죽였을 때 같은 운행이 이력 두 건으로 갈린다.**
운행의 경계는 기사의 종료이지 서비스가 몇 분 만에 되살아났는가가 아니다.

### 이력이 지저분해지던 두 원인

실측에서 11회 운행 중 실제 운행은 1건이고 나머지가 `0.0 km · 진행 중` 이었다.

1. 절전 정책이 프로세스를 죽이면 `stopCollection()`이 돌지 못해 `ended_at`이
   빈 채 남는다. 빈 운행 삭제가 마감 시점에만 돌아 영원히 쌓였다.
   서비스 시작 때 `closeOrphanTrips()`로 닫는다. 종료 시각은 마지막 이벤트
   시각을 쓴다 — 지금 시각을 쓰면 며칠 전 죽은 운행이 "5일 12시간"이 된다.
2. 삭제 기준이 거리 100m뿐이라 GPS 잡음으로 넘기 쉬웠다. 거리 800m와 3분을
   모두 밑돌면 지운다. 다만 걸린 항목이 하나라도 있으면 짧아도 남긴다.

## 12. 판정 신뢰도 — 실측 기반 평가

2026-09-11에 처음으로 공식 eTAS 점수와 대조했다. 그 결과를 반영한 등급이다.

| 항목 | 등급 | 근거 |
|---|---|---|
| 급감속 | **상** | 공식 0.97 vs 앱 1.62 (오차 범위 안) |
| 과속 | 상 (매칭 성공 시) | 마진 20km/h가 커서 GPS 오차에 둔감. 단속카메라로 보정 |
| 장기과속 | 중 · 미탐 편향 | 터널에서 게이트가 막히면 타이머 리셋 |
| 급정지 | 미검증 | 1건 보려면 141km 필요. 하루치로 판단 불가 |
| 급좌우회전 | 미검증 | 정렬이 끝나야 판정된다. 실측 0건 |
| 급U턴 | 미검증 | 시내버스에서 드물어 표본이 없다 |
| 급출발 | 하 | "5.0km/h 이하"가 잡음 구간과 정면으로 겹침 |
| **급가속** | **하 · 명확한 오탐** | **공식 한 달 0.00건인데 앱은 하루 47건** |

**급가속이 자주 뜨면 운전이 거친 게 아니라 측정이 틀렸다.** 추정이 아니라
공식 데이터로 확인된 사실이다. 시내버스 0-50km/h가 12~18초라 평균 1.0 m/s²,
저속 피크도 1.5 m/s² 수준인데 기준표는 6~8 km/h/s(1.7~2.2 m/s²)를 요구한다.

### 판정하지 않는 유형

급진로변경·급앞지르기·연속운전은 판정하지 않는다. 그런데 144번 기사의 공식
점수에서 **급진로변경이 1.29로 단일 최대 항목**이었다. 합계 3.55의 36%다.

즉 이 기사에게 "당신의 주된 위험 습관"을 알려주려면 급진로변경을 봐야 하는데
지금 앱은 그것을 놓치고 있다. 진단 모드로 자이로 원시값은 저장하고 있다.

### 확인된 실차 동작

- 좌표계 보정 **100% 완료** (방향 집중도 18.5 / 기준 4.0)
- 재보정 **20회 → 0회** (거치 변화율 제외 후)
- 정렬 완료 구간 경고율 **68% → 6%**
- 도로 데이터 매칭 정상, 감지 중단 **0초**
- 공식 eTAS 급감속과 오차 범위 안에서 일치

### 남은 과제

1. **급가속 임계값** — 공식은 한 달 0.00건인데 앱은 하루 47건. 기준표는 공단
   값이라 임의로 조정하지 않는다. 억제 로직으로 다뤄야 하는데, 어느 쪽으로
   조일지는 정답 라벨이 있어야 정한다.
2. **146번 기기에서 정렬 실패** — 전방축 샘플이 0에서 움직이지 않는다.
   정합 오차 프레임 37건이 유일한 단서다. 원인 미상.
3. **한 달치 데이터 수집** — 하루치로는 급감속 말고 아무것도 검증할 수 없다.
   같은 달 공식 점수와 대조하면 기간 불일치 문제도 사라진다.
4. **급진로변경** — 공식 기준 최대 위험 항목인데 판정하지 않는다.
5. **화면 끄고 8시간 운행 시험** — 시험 기기에 wake-up 센서가 없다.
6. **배터리 소모 측정** — 배칭 지연 1초를 유지할지 이 측정 후에 정한다.
7. **운행 지역 확장** — 현재 DB는 위도 36.10~36.60, 경도 127.20~127.65다.

## 14. 원칙

한 문장으로 줄이면 **"확실하지 않으면 경고하지 않는다"** 입니다.

- 제한속도 구간 매칭 실패 → 과속 판정 보류
- 맵매칭 후보가 모호 → 보류
- 판정값이 GPS 잡음 대비 부족 → 보류
- 차량 성능 초과 → 보류
- 어린이보호구역 근처인데 제한속도가 높음 → 보류
- **IMU 종가속도와 어긋남 → 보류**
- **전방축 부호를 믿을 수 없음 → IMU 교차검증 자체를 쓰지 않음**
- 게이트 차단 → 경고 없이 기록만

**보류된 건도 사유와 함께 전부 저장됩니다.** 그래야 한 번의 운행이 다음 수정의
근거가 됩니다. 이 문서의 5~11절은 전부 그렇게 나온 것입니다.

2026-09-09 하루 데이터에서 경고는 3건이었지만 기록은 121건이었습니다.
**경고만 저장했다면 급가속이 틀렸다는 것도, 전방축 부호가 뒤집혔다는 것도
알 수 없었습니다.**

다만 기사 화면에는 경고 건수만 보여 줍니다. 기사에게 필요한 것은 "오늘 몇 번
혼났나"이고, 보류 건수는 그 판단을 흐립니다. 분석은 이력과 CSV에서 합니다.

그리고 이 앱의 판정은 한국교통안전공단 eTAS의 공식 판정이 아니라 휴대폰 센서로
계산한 추정치입니다. 자기점검 용도이며 회사의 감시·평가 도구가 아닙니다.
모든 데이터는 기기 안에만 저장되고 외부로 전송되지 않습니다.
