### 빌드
```bash
cd "E:/app/11. eTAS" && ./gradlew assembleDebug lintDebug
```
- APK는 `app/build/outputs/apk/debug/safedrive-v<버전>-debug.apk`. 클린 빌드 5~10분.

### 2.3 전방축 부호 검증은 "돌았지만" 신뢰 구간에 못 들어왔다

CSV `판정값` vs `IMU피크_kmh_per_s` 부호 대조 (정렬 완료 구간):

| | 146번 | 144번 |
|---|---|---|
| 전체 일치율 | **52%** (42/80) | **56%** (46/82) |
| 급정지 | 86% | 79% |
| 급출발 | 75% | 67% |
| 급가속 | 53% | 49% |
| 급감속 | 21% | 56% |

30~70% 구간이므로 설계대로 **뒤집지도, 신뢰하지도 않는다**. 즉 `SIGN_TRUST_RATIO`
게이트에 막혀 IMU 교차검증이 하루 종일 꺼져 있었다.

**부호가 흔들리는 이유는 축이 비스듬해서가 아니라 대조에 쓰는 통계량이 틀렸다.**

- 정렬 완료 구간 `IMU피크` 크기의 **중앙값이 0.55~0.62 m/s²** 다. 실제 버스 종가속도가
  그 수준이라는 뜻이고, WORKLOG 5.12의 관측과 같다.
- 그런데 `peakLongitudinal()`은 1초 창의 **절대값 최대**를 고른다. 노면 진동 스파이크가
  ±1.5~2.9 m/s²로 들어오면 진짜 신호(0.6)를 덮는다.
- 실제로 급가속 이벤트의 **47~51%에서 IMU 부호가 반대**였다. 신호보다 잡음이 큰
  동전 던지기다.

→ **대조 통계량을 창 평균(또는 저역통과 후 부호방향 극값)으로 바꿔야 한다.**
   peak는 "진짜 이벤트면 평균보다 작을 수 없다"는 원래 논리에는 맞지만,
   잡음이 신호보다 큰 지금은 그 논리가 성립하지 않는다.

### 2.4 그래서 경고가 다시 폭증했다

| | 정렬 완료 구간 경고율 |
|---|---|
| 144번 (v0.16, WORKLOG 5.18) | **6%** |
| 144번 (v0.22, 09-13) | **44%** |
| 146번 (v0.22, 09-12) | **89%** |

WORKLOG 5.16에 적어 둔 우려 — *"억제가 많이 걸린 것도 운 좋게 맞은 것일 수 있다"* —
가 그대로 확인됐다. **6%는 무작위 억제의 산물이었다.** 부호를 못 믿을 때 억제를
끄도록 고친 것은 정직한 조치지만, 그 결과 억제력이 통째로 사라졌다.

수평 가속도 크기 폴백은 설계대로 "한쪽으로만" 틀렸다 — 146번에서 14건,
144번에서 42건만 걸렀다. 노면 진동이 크기를 키우는 방향이라 예상대로 약하다.

|---|---|---|---|

같은 기사·같은 노선인데 억제가 꺼지면서 24.5/100km가 됐다.

### 2.6 급출발은 판정 신호가 구조적으로 틀렸다 (새 발견)

`판정값 ≈ 현재속도`인 건, 즉 **직전 1초 속도가 0이었던 건**의 비율:

| | 비율 |
|---|---|
| 144번 | 14/19 = **74%** |
| 146번 | 28/48 = **58%** |

버스는 0 → 8~12 km/h를 1초에 낼 수 없다(2.2~3.3 m/s², 물리 한계 1.0~1.5).
원인은 둘이 겹친 것이다.

1. **정차 잡음 억제 clamp** (`MotionEstimator.suppressStationaryNoise`) — 보고 속도가
   속도정확도(1σ)보다 작으면 0으로 만든다. 출발 직후 몇 초가 0으로 눌린다.
2. **도플러 지연 0.5~1초** — 눌려 있던 속도가 한꺼번에 올라온다.

결과적으로 **정상 출발이 1초짜리 계단**이 되어 급출발 임계 8 km/h/s를 그대로 넘는다.
공식 급출발은 0.06/100km인데 앱은 7.7이다.

### 2.7 과속 오탐의 새 패턴 — 같은 도로인데 링크마다 제한속도가 다르다

> **2026-09-14 정정:** 아래는 가설이었고 확인되지 않았다. 이후 반복 지점 두 곳
> (보문로, 산내로1257번길)을 현장 확인한 결과 실제 제한속도가 DB와 같은 30km/h였다.
> 그 두 곳의 과속은 정탐이다(4.4). 09-13의 세 지점은 따로 확인하지 않았다.

144번 과속 3건은 모두 **제한 30 링크에 매칭**됐고 속도는 50.0~55.3 km/h,
GPS 정확도는 3.9~4.2m로 좋았다. 도로DB에서 그 지점 주변을 뽑아 보면:

```
11:08 지점  제한 50 대종로(12) · 50 대전로(9) · 50 동구청로(9)
            제한 40 대전로(10) · 제한 30 대전로(4)   <- 같은 대전로인데 50/40/30이 섞여 있다
```

간선(제한 50)을 달리다 **같은 이름의 제한 30 링크**에 붙은 것이다. WORKLOG 5.8에서 넣은
"제한 30 **미만**이면 보류"는 정확히 30인 이 경우를 걸러 주지 못한다.

### 2.8 진단 수치 하나가 단위를 잘못 쓰고 있다

`과속 판정 보류 N 샘플`이 **프레임 카운터**다. 144번 6시간 37분 운행에 765,570 —
초당 32회다. 기사도 개발자도 이 숫자로는 아무 판단을 할 수 없다.
**보류된 시간 비율(%)로 바꿔야 한다.**

## 3. 2026-09-13에 넣은 수정 (v0.23.0) — 전부 검증 대기

분석 근거는 2절이다. **한 번에 하나씩만 바꿨다.** 세 가지를 동시에 고치면
다음 운행에서 무엇이 들었는지 못 가린다.

### 3.1 IMU 대조를 피크 → 창 평균으로 (2.3이 근거)

| 파일 | 바꾼 것 |
|---|---|
| `MotionHistory.kt` | `meanLongitudinal()` 추가. `peakLongitudinal()`은 기록용으로 유지 |
| `JudgementEngine.kt` | `alignedMismatch` 판단을 평균으로 |
| `FrameAligner.kt` | 부호 검증에 **2Hz 저역통과**를 건 종가속도를 쓴다 (기존엔 원시값) |

부호 검증이 원시 가속도를 쓰고 있었다는 게 이번에 찾은 것이다. 판정에 쓰는 값은
`MotionEstimator`에서 필터를 거치는데, `FrameAligner.verifyForwardSign()`은 필터 이전
단계라 진동이 그대로 들어갔다. **같은 것끼리 비교하지 않고 있었다.**

### 3.2 급출발 계단 차단 (2.6이 근거)

판정 창 안에 정지 잡음 억제로 눌린 속도가 있었으면 급출발을 `정지 잡음 억제 해제 계단`
사유로 보류한다(`MotionHistory.hadSuppressedSpeed()`). 기록은 그대로 남는다.

목표는 공식 0.06/100km와 같은 자릿수다. 지금 7.7은 명백한 오탐이다.

### 3.3 기록 보강 — 다음 판단의 재료 (2.7·2.3이 근거)

| 컬럼 | 왜 |
|---|---|

### 3.5 진단 파일 자동 저장 (v0.24.0)

진단 탭 스크린샷을 없앴다. 스크린샷은 운행 종료 전에, 폰을 거치대에서 떼지 않고,
정차 후 3분 안에 찍어야 했다. 떼면 거치 편차가 올라가 재보정이 걸리고(실측: 캡처 중
22.3°), 늦으면 값이 다음 운행 것으로 바뀐다(실측: `총 운행 38초` 캡처).

운행이 끝나는 순간 서비스가 **다운로드/SafeDrive/** 에 저장한다.
끝나는 경로는 3분 정차 팝업·알림의 `운행 종료`, 뒤로가기 → 종료 확인, 상시 알림의 `정지`,
설정 탭의 수집 정지, 자정 분리다. **주행 탭에는 정지 버튼이 없다.**

| 파일 | 내용 |
|---|---|
| `safedrive_trip_<시작>_report.txt` | 운행 요약 · 유형별 건수/100km · 보류 사유별 · **IMU 부호 대조(평균/피크)** · 좌표계 보정 · 게이트 · 센서 |
| `safedrive_trip_<시작>_events.csv` | 이번 운행 이벤트만 (CSV 내보내기와 같은 컬럼) |

- 부호 대조는 2절에서 손으로 하던 분석을 그대로 넣었다. 평균과 피크를 나란히 보여 줘
  3.1의 수정이 들었는지 리포트 한 장으로 판단된다.
- 진단 탭 `운행 중 지금 저장` 버튼으로 운행 중에도 저장할 수 있다(파일명에 저장 시각).
- **절전 정책이 프로세스를 강제로 죽인 운행은 남지 않는다.** 마감 코드가 돌지 못하기
  때문이다. 그때는 이력 탭의 CSV 내보내기로 이벤트만 꺼낸다.

저장 조건 상세:
- **운행마다 파일이 따로 생긴다.** 하루 3회 운행·종료면 파일 6개. 이전 운행 데이터는 섞이지 않는다.
  하루 전체를 한 파일로 원하면 이력 탭의 `CSV 내보내기`(최근 30일)를 쓴다.
- 좌표계 보정·부호 일치는 **운행 시작 때 초기화**된다. 자정 분리는 앱이 재시작되지 않으므로 이어진다.
- 저장되지 않는 경우: 빈 운행(이벤트 0건이면서 100m 미만, 또는 800m·3분 미만이면 운행 자체가 삭제),
  최근 앱 목록에서 밀어서 끔(서비스는 계속 돌아 운행이 끝나지 않음), 절전 기능의 강제 종료,
  종료 직후 1~2초 안에 전원을 끔.

- 결과는 운행 종료 시 `_shadow.csv`와 리포트의 `[그림자 판정]` 절에 남는다.

2. **미탐 여부.** `_shadow.csv`가 비어 있거나 극소수면 지연 보정값(700ms)이 틀렸을 수 있다.
   원시 기록으로 오프라인에서 다시 맞춘다.
3. **146번 거치 개선 효과.** 원시 수평피크 중앙값 2.83 → 1.5 근처로 내려오는지,
   보정이 완료되는지, 부호 일치 70%를 넘는지.

전환 결정은 이 세 가지를 보고 한다. 결과가 나쁘면 `ShadowJudge`만 지우면 된다.

## 11. 설계 판단 기록 (2026-09-15 ~ 16)

코드 변경 없이 대화로 분석·결정한 것들이다. 같은 질문을 다시 하지 않도록 남긴다.

### 11.1 앱이 백그라운드일 때도 경고가 나가는가

**코드상으로는 나간다.** 포그라운드 서비스(`foregroundServiceType=location`) 안에서 센서를 등록하고,
센서 스레드에서 판정한 뒤 `DrivingService.onJudgedEvent` → `AlertManager.warn`이 바로
진동·경고음(2.2kHz)·음성(`USAGE_ASSISTANCE_NAVIGATION_GUIDANCE`)을 낸다.
화면이 켜져 있는지, 앱이 앞에 있는지 보는 조건은 없다.

**실측:** v0.24.0 5회(9시간 53분) 모두 감지 중단 0초 · 전달 지연 0초 · 서비스 재시작 0회.

**확인되지 않은 것:**
1. 그 시간 동안 **화면이 꺼져 있었는지 모른다.** 리포트에 화면 상태가 없다.
2. 두 기기 모두 **non-wakeup 센서, 자이로 FIFO 0**이고 `화면 꺼짐 시 수집 강제 유지`는 기본 꺼짐.
   화면이 꺼져 CPU가 잠들면 자이로부터 끊길 수 있다. 1초 GPS 갱신이 CPU를 깨워 버티는지는 미확인.
3. 음성·진동이 **실제로 나갔는지 기록이 없다**(오디오 포커스 획득, 발화 완료).
4. 진동을 용도 지정 없이 호출한다. **무음·방해금지 모드에서 막힐 수 있다.** 사용자 스크린샷 상태바에
   무음 아이콘이 있었다. 음성은 내비게이션 용도라 미디어 볼륨을 따른다.

**제안(미구현, 사용자 결정 대기):** 이벤트별 경고 시점 화면 상태, 운행별 화면 꺼짐 비율,
강제 유지·배터리 최적화 제외 여부, 발화 결과, 무음 모드·미디어 볼륨을 기록하고,
화면을 끈 채 1회 현장 시험.

### 11.2 GPS 방식의 원리적 한계

eTAS의 DTG는 바퀴 회전 신호로 속도를 잰다(지연·잡음 거의 없음). 휴대폰 GPS는 그렇지 않다.

| | 값 |
|---|---|
| 급가속 기준 (21km/h 초과) | 6 km/h/s |
| 시내버스 실제 출발 가속 | 약 3.6 km/h/s (1.0 m/s²) |
| GPS 속도정확도 (CSV 대부분) | 0.2~0.4 m/s → 1초 차분 오차 **약 1.5 km/h/s** |

여유 2.4에 잡음 1.5 → **정상 가속 1초마다 약 5%가 잡음만으로 기준을 넘는다.** 시간당 가속 100초면
하루 40건대. 144번 억제 전 급가속 **하루 47건**, 공식 **한 달 0.00건**과 규모가 맞는다.
구조적 왜곡도 있다: 수신기 평활화로 급정지 약 4배 과대평가, 정지 잡음 억제 해제 계단(급출발 오탐 58~74%).
**억제 로직은 "GPS가 틀렸을 때 막는" 것까지만 할 수 있고 정확한 값을 만들지는 못한다.**

| 유형 | 판단 |
|---|---|
| 과속 | 가능성 높음. 일정 속도 GPS ±1~2km/h, 여유 20km/h. 현장 확인 2곳 정탐 |
| 급좌우회전·급U턴 | 가능성 높음. 자이로 직접 측정. 실측 표본 0건 |
| 급감속·급정지 | IMU 중심이면 가능 |
| 급가속·급출발 | GPS로는 불가, IMU 중심이면 조건부 |
| 급진로변경 | 미개발 (144번 공식 최대 항목 1.29) |

**현실적 목표:** 건별 일치는 불가능하다(센서가 다르고 기준 근처 건은 어느 장비든 갈린다).
**한 달 누적 100km당 건수가 유형별로 같은 자릿수**이고 **빈도 순위가 같으면** 성공으로 본다.
같은 달 공식 점수와 대조해야 한다.

### 11.3 거치 방향과 거치대

**보정 계산은 폰 방향과 무관하다(코드 확인).** 수평면 기준축 `Vec3.anyPerpendicular`는 중력과 가장
덜 정렬된 축(X, 거의 X면 Y)을 골라 투영·정규화한다. 최악의 경우도 길이 44%로 수치적으로 안정.
방향 집중도는 기준축 선택과 무관하고, 화면 회전·좌표계 변환 코드도 없다.

**물리적으로는 세로 거치가 불리하기 쉽다.** 무게중심이 고정점에서 멀어 까딱임이 커진다.
까딱임은 폰 위치에 실제 직선 가속을 만들어 중력 제거로 없어지지 않는다.
예: 고정점 10cm · 초당 8회 · 0.5° → 약 2.2 m/s². 146번 수평 중앙값 2.83과 같은 크기.

| | 거치 | 수평 중앙값 | 부호 일치 |
|---|---|---|---|
| 144번 | **가로, 짧은 클램프, 차체 레일 고정** (09-16 사진) | 1.45 | 89% |
| 146번 | 세로 | 2.83 | 52% |

→ 146번에 144번 방식을 권했다. 단, 버스 차종·노면 차이일 가능성도 남아 있어 비교 운행으로 확인한다.

**기종 차이:** 가속도계 잡음은 1초 평균이면 보급형도 무시할 수준. 분기점은 ① 자이로 유무
(없으면 `TYPE_GRAVITY`·저역통과 폴백으로 장시간 가감속을 중력으로 오인, 회전 판정 불가)
② wake-up·배칭(화면 꺼짐 연속성) ③ 거치. **배포 시 최소 조건은 자이로 탑재.**

### 11.4 융합 방식 장단점과 그림자를 고른 이유

| 장점 | 단점·위험 |
|---|---|
| 도플러 지연·정지 잡음 계단 같은 구조적 오탐 제거 | **미탐 위험** — IMU 기준 100%에서 0건(9절) |
| 급정지 과대평가 해소 | **정렬 의존 심화** — 정렬이 안 되면 경고 자체가 없어진다(146번) |
| 1초 판정 잡음 대폭 감소 | 자이로 없는 기기 사용 불가 |
| 저속(급출발·급정지) 정확 | 도로 경사 잔차 (5% = 1.8 km/h/s, GPS로 교정) |
| 판정 근거 단일화 | 개발·검증 비용, 경고 이유 설명이 어려워짐 |
| GPS 끊김 구간에서도 수 초 유지 | |

과속·회전·기록 구조는 영향이 없다. 위험은 가감속 4종에 한정된다.

**결정:** 바로 전환하지 않고 **그림자 판정**으로 같은 운행에서 두 방식을 나란히 계산한다(10절).
기사 운행에 영향이 없고, 결과가 나쁘면 `ShadowJudge`만 지우면 된다.
